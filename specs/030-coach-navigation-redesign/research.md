> Phase 0 output. Builds on `specs/028-frontend-design-foundation/research.md` (shared program base — PageHeader, shadcn primitives, design tokens, testing infra; not repeated here) and the audit evidence in `docs/17-coach-ux-redesign/agent-reports/03-information-architecture.md` + `proposal.md` §4. ## R1. Collapsible sidebar groups — disclosure mechanism

- **Decision**: new `frontend/src/components/ui/collapsible.tsx` (shadcn-standard Root/Trigger/Content wrapper, `forwardRef` + `cn()`, same convention as `sheet.tsx`/`dropdown-menu.tsx`), sourced via `import { Collapsible as CollapsiblePrimitive } from "radix-ui"` — the umbrella meta-package already a **direct** dependency (`frontend/package.json:75`, `"radix-ui": "^1.4.3"`). `SidebarNav` wraps each multi-item area in `Collapsible.Root open={isExpanded}`; the single-item Inicio area renders as a plain `NavLink`, no disclosure chrome. Two independent controls per multi-item area: the area **label** is a `NavLink to={resolveAreaDefaultTo(area, role)}` (navigates); a separate 44×44px chevron button (`aria-expanded`, `aria-controls`) toggles disclosure only — split so one control never does two unrelated things.
- **Auto-expand rule**: `isExpanded = isAreaActive(area, location.pathname) || manuallyOpened[area.id]`; `isAreaActive` does longest-prefix match over `area.matchPrefixes` (R4).
- **Availability verified without `node_modules/`** (this sandbox has none installed — same limitation 028-R1 recorded for the shadcn registry): `@radix-ui/react-collapsible@1.1.13` resolves in `frontend/package-lock.json:1784`, and `@1.1.12` in `frontend/pnpm-lock.yaml:845`, both as a transitive dep of the `radix-ui` umbrella (`package-lock.json:8058`, `radix-ui@1.5.0 → @radix-ui/react-collapsible@1.1.13`). It ships at **zero new top-level dependency**. It is *not* its own top-level `package.json` entry, so importing `@radix-ui/react-collapsible` directly would be a phantom-dependency risk under pnpm's strict linking (the repo carries both a `package-lock.json` and a `pnpm-lock.yaml`); importing the `Collapsible` export from the already-direct `radix-ui` umbrella avoids that risk entirely.
- **Rationale**: reuses a primitive the project effectively already ships; gets tested a11y (Enter/Space, `aria-expanded`, `data-state`) and height animation for free, respecting the project's global `prefers-reduced-motion` handling.
- **Alternatives considered**: native `<details>/<summary>` — zero JS, but its default triangle marker is hard to restyle to match the existing nav row, and syncing browser-native `open` with route-driven auto-expand fights the element's own state model; kept as a documented fallback only. shadcn's full `sidebar.tsx` block — rejected per 028-R1's explicit deferral ("030 decides sidebar"): it bundles its own context/provider/cookie-persisted state and mobile-sheet wiring, a far bigger replacement than the label/grouping change FR-009 calls for.

## R2. Bottom tab bar (mobile/tablet)

- **Decision**: new `frontend/src/components/layout/BottomNav.tsx` — `<nav aria-label="Navegación principal" className="fixed inset-x-0 bottom-0 z-40 … md:hidden">`, 5 slots (4 areas + "Más"), each a `NavLink`/button ≥48×48px; `NavLink`'s built-in `aria-current="page"` marks the active slot. Breakpoint: `md` (768px Tailwind default) — the same token `AppShell.tsx` already uses (`md:static`, `md:hidden`), so no new convention. Safe area: `pb-[env(safe-area-inset-bottom)]` on the bar; `<main>` gets matching bottom padding below `md` so content is never trapped under it. "Más" opens the existing `ui/sheet.tsx` (`side="bottom"`) — already a dependency with zero non-`ui/` importers today — listing remaining areas + Mi perfil + Cerrar sesión + Salud IA (admin).
- **Coach slots**: Inicio, Entrenamiento, Competencias, Atletas, Más. **Admin slots**: Inicio, Entrenamiento, Competencias, **Biblioteca**, Más (R6).
- **Keyboard/OSK coexistence**: no coach page today places a persistent input directly above a fixed bottom region (attendance/rubric flows are full-page, not modal-over-bar); dialogs/sheets already portal above the bar (`z-50` > bar's `z-40`) with Radix's focus trap. Real on-screen-keyboard occlusion can't be simulated in jsdom/Playwright — documented as a **manual** quickstart check, not an automated gate.
- **Rationale**: `<nav>` + `aria-current` + 48px is the standard accessible bottom-tab-bar recipe; `fixed` (not `sticky`) survives iOS Safari's chrome-collapse-on-scroll, unlike the header's `sticky top-0` (used there for a different, reveal-on-load reason).
- **Alternatives considered**: one bottom `Sheet` "app drawer" for everything (rejected — defeats the one-thumb-tap promise of SC-004); `position: sticky` (rejected — depends on a correctly sized scroll ancestor and can scroll away).

## R3. User menu + quick-create

- **Decision**: both on the existing `ui/dropdown-menu.tsx` (`@radix-ui/react-dropdown-menu`, direct dependency). **User menu** replaces the two standalone header buttons (`AppShell.tsx:279-293`, "Mi perfil" / "Cerrar sesión") with one trigger (name + chevron) → items: "Mi perfil" (`/perfil`, all roles) · separator · "Salud IA" (`/admin/ai`, admin-only) · separator · "Cerrar sesión" (all roles). **Quick-create** is a new header icon button (`Plus`, `aria-label="Crear"`) → role-filtered items: "Nueva sesión" (`/training/sessions/new`), "Nueva competencia" (`/competitions/new`), "Nuevo evento" (`/calendar/events/new`) — coach+admin — and "Nuevo atleta" (`/athletes/new`) — coach-only. No `?prefill` query params are populated by any of the 4 targets today (each opens its existing blank form; the calendar day-click prefill from 028-R11 is a different, already-contextual entry point) — the contract documents the param as reserved for a future contextual launch, not wired now.
- **Rationale**: reuses the exact primitive (and its Radix a11y: roving tabindex, Esc, focus return) — no new component; matches 028's consumption map ("030 navigation: … user menu + quick-create built on existing dropdown-menu").
- **Alternatives considered**: two separate specialized popovers — rejected, more code for an identical need; the point of FR-006 is consolidating two standalone buttons into one.

## R4. Area→default-view routing, active-state, and the sibling-view pattern

- **Decision**: `NavArea.defaultTo` is a *preferred* target, resolved at render by `resolveAreaDefaultTo(area, role)`: if its owning item is role-visible, use it; else fall back to the first `items[]` entry the role can see. Active-state/auto-expand uses longest-prefix match over `area.matchPrefixes`. Sibling views (Calendario ↔ Sesiones ↔ Actividades; Válidas ↔ Sin enlazar ↔ Panorama de temporada) share one new component, `frontend/src/components/layout/SiblingViewTabs.tsx`, promoting the existing pill pattern (`@radix-ui/react-tabs`; `TAB_LABELS`/`TAB_VALUES` at `frontend/src/routes/competitions/CompetitionDetailPage.tsx:95-112`, the `TabTrigger` sub-component at `:158-172`, rendered at `:641`) — visually distinct from per-record detail tabs, which stay untouched. It renders as its own full-width row directly under the page `<h1>`, **not** inside `PageHeader`'s `actions` slot: per `specs/028-frontend-design-foundation/contracts/shared-components.md`, `actions` is right-aligned/button-shaped, while sibling nav is left-aligned multi-item wayfinding — mixing the two breaks reflow under ~380px, and the existing pill row already sits full-width below the header for the same reason. Because each sibling view is a real route, "preserve active view on refresh/back" (FR-003) falls out for free.
- **Non-obvious risk caught and resolved**: Familias is the *only* area whose spec-designated default item (Padres, `/parents`, coach-only per `App.tsx:297-303`) is hidden for a role the area itself stays visible to (admin sees Boletines/Informes del club). Without the fallback above, an admin clicking the "Familias" label would land on `/parents` and be silently bounced by `ProtectedRoute` — reintroducing the exact dead-click bug 028 fixes elsewhere in the app. The fallback (first role-visible item) sends admin to Boletines instead, with no hardcoded per-role branch in the config.
- **Alternatives considered**: an index/hub page per area — rejected, the anti-pattern this program removes (regresses SC-003); sibling tabs inside `PageHeader.actions` — rejected, wrong affordance shape and narrow-width collision.

## R6. Admin's 4th bottom-bar slot (US3 Acceptance #3)

- **Decision**: **Biblioteca**, not Familias.
- **Rationale**: the source IA report leaves this open ("the 4th tab becomes Biblioteca or Familias," `agent-reports/03-information-architecture.md:154`). Familias' spec-designated default item is Padres, coach-only; Biblioteca's default (`/technique`, `App.tsx:673-688`) is coach+admin with no role branching, so it needs none of R4's fallback machinery just to avoid a first-tap dead end. Familias stays fully reachable for admin from the sidebar/"Más" sheet; only the bottom bar's 4th physical slot differs by role.

## R7. Anxiety demotion — admin nav-reachability trade-off (flagged, not silently resolved)

Per spec Acceptance Scenario US1-5, the whole "Atletas" area (new home of "Ansiedad competitiva") is coach-only and **absent** for admin — matching constitution Principle V's stated intent ("access MUST be restricted to the coach"). Today, though, admin **does** see a top-level "Ansiedad competitiva" `NavLink` (`AppShell.tsx:111-119`, gated `isCoach || isAdmin`). Grouping it under a coach-only area removes admin's nav path to `/anxiety`, while the route itself stays `allowedRoles={[admin, coach]}` (`App.tsx:241-247`, unchanged — FR-009 forbids permission changes). This is a deliberate, spec-directed choice, not an oversight: the spec edge case's "reachability… identical" refers to the *consented, coach-mediated* workflow, and Principle V already names the coach as the intended actor. Recorded so a reviewer can override explicitly if admin nav access was actually meant to persist.

## R9. Cross-reference — Panorama de temporada entry point (029 vs. 030)

029's own FR-002 gives the season page "a visible entry from the Competencias area" — read as a minimal in-page link (proposal §Quick-Wins: "Análisis IA entry in `CompetitionsListPage`'s action row"). 030 does not duplicate that; it *promotes* the same destination to a first-class `NavItem` (sidebar sub-item + `SiblingViewTabs` pill) so it also survives auto-expand/active-state and the mobile "Más" sheet. The item's `to` is computed via the `currentSeason()` helper 028-R11 introduces in `lib/datetime.ts` (not yet present — confirmed by reading the file's current exports), avoiding a fourth hardcoded-year site alongside the one already flagged in `InsightsHubPage.tsx:18` (moot once 029 deletes that file).
