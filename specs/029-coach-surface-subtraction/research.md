## R2. `SeasonInsightsPage` relocation

**Decision**: Move `routes/competitions/insights/SeasonInsightsPage.tsx` (196 LOC) to `routes/competitions/SeasonInsightsPage.tsx`. Keep the route path unchanged (`/competitions/insights/season/:year` — it is just a literal string to React Router, not a nested hierarchy; changing it would need a redirect for zero benefit). Add a "Panorama de temporada" secondary-action link to `CompetitionsListPage.tsx`'s header action row (:192–211, alongside the existing "Cargar resultados"/"Sin enlazar" links at :193–202/:203–211), pointing at `/competitions/insights/season/${currentSeason()}` (reuse the `currentSeason()` helper from `lib/datetime.ts`, feature 028 R11 — do not hardcode a year).

**Two internal dead links found by direct inspection (not in the audit)**: `SeasonInsightsPage.tsx:29–36` back-link targets `/competitions/insights` (the deleted hub) — retarget to `/competitions`. `SeasonInsightsPage.tsx:156–158` (`onClick` on each athlete row) navigates to `/competitions/insights/athletes/${it.athlete_id}` (the deleted `AthleteInsightsPage`) — retarget to `/athletes/${it.athlete_id}?tab=ai_analysis`, the surviving per-athlete analysis home (`AthleteDetailPage`'s `ai_analysis` tab, which mounts `AthleteAIAnalysisTab` — same component `AthleteInsightsPage.tsx:7-8` reused "in coach mode"). Both are one-line changes but load-bearing: without them the surviving page would silently 404 on its own back-link and its main interaction.

**Rationale**: the audit already established `SeasonInsightsPage` as the one non-duplicated view in the hub (season-long per-athlete table — races run, podiums, best position, points — available nowhere else); this decision only adds the two link fixes the relocation makes necessary and picks the concrete new entry point location.

**Alternatives considered**: changing the route path to drop the `insights` segment (rejected — free churn, no user-facing benefit, and would need its own redirect); placing the new entry point in the sidebar/nav (rejected — out of scope, nav regrouping is feature 030; a page-level action link is the smallest change consistent with "give it a visible entry from Competencias").

## R4. Anxiety on-demand interpretation wiring (D2)

**Decision**: In `IndividualPanel.tsx` (rendered by `AnxietyDashboardPage`'s `IndividualTab`, :127), compute `latest = series.points.at(-1)` (already done at :20 for flags) and, when `latest` exists, render `<AnalyzeButton assessmentId={latest.assessment_id} onAnalyzed={setResult} />` beneath the scores table, gated on `latest.cognitive !== null` (see below), then render `<InterpretationPanel interpretation={result.interpretation} source={result.source} />` on success. Both components are already built, functional, and simply never mounted (`AnalyzeButton.tsx` 54L, `InterpretationPanel.tsx` 90L; `useInterpretation` hook `hooks/anxiety/useAnxietyAssessments.ts:85-94`; `interpretAssessment` API call `api/anxiety.ts:85-95` → backend `POST /assessments/{id}/interpret`, `backend/app/routers/anxiety.py:431-453`) — confirmed zero existing importers/tests for either component before this change.

**Why the `cognitive !== null` gate**: `IndividualPanel` only has `series: AthleteSeries` (from `GET /athletes/{id}/series`, `routers/anxiety.py:487-534`), whose `SeriesPoint` (`types/anxiety.types.ts:101-109`) carries scores but not `status`. The backend's only guard on `/interpret` is `assessment.status == pending` → 422 "La evaluación aún no tiene respuestas para interpretar" (`routers/anxiety.py:442-446`); a pending (zero-answer) assessment has null subscale scores, so `cognitive !== null` is a reliable frontend-only proxy for "interpretable" without a backend change.

**Consent-gate reality (verified precisely, and more limited than it first appears)**: guardian consent for `psychological_assessment` is checked **only at assessment creation** (`create_assessment` → `has_psychological_consent`, `backend/app/services/anxiety/assessments.py:114-115` → `consent_gate.py:21`). Neither `read_assessment`, nor `athlete_series`, nor `interpret_one` (`routers/anxiety.py:357-364,487-534,431-453`) re-check consent — this is true of the *entire* already-shipped read surface, not something this feature introduces. There is also no coach-facing "does athlete X currently have psychological consent" signal anywhere in the frontend: the only consent-status endpoint, `GET /api/me/consent`, is parent-scoped (`_only_parent`, `backend/app/routers/consent.py:35,70-79`), and `AthleteOut.parental_consent_obtained` (`backend/app/schemas/athlete.py:59`) is an unrelated general onboarding flag, not the granular `psychological_assessment` grant. **Given FR-009 mandates no server-side changes**, this feature cannot add a proactive "is consent still current" check; it inherits exactly the safeguard posture the rest of the (audited, tested) anxiety module already has today — an assessment's existence is proof consent existed at creation, and the existing `mapAnxietyError` 409→`consent_missing` mapping (`api/anxiety.ts:170-171`) is reused as-is for defensive/forward-compatible error display if the backend ever returns 409 from `/interpret`. The literal mid-session-revocation edge case (spec.md Edge Cases) is therefore **not newly closed by this feature** — it was never closed anywhere in the module — and is called out here explicitly rather than silently assumed solved; closing it fully would require a backend consent re-check, out of scope per FR-009.

**Error-copy risk found and resolved**: `mapAnxietyError`'s 422 branch (`api/anxiety.ts:172-173`) is hardcoded to the assessment-creation "instrument override needed" message, which would misrepresent a hypothetical `/interpret` 422. The `cognitive !== null` button gate above makes that 422 effectively unreachable in normal use, so no change to `mapAnxietyError` itself is needed.

**Test-harness gap found**: `IndividualPanel.test.tsx`'s 5 existing tests (:71,81,88,97,102) render `<IndividualPanel>` with no `QueryClientProvider`; `AnalyzeButton`'s `useInterpretation` calls `useMutation`, so every existing test needs a `QueryClientProvider` wrapper added, plus a new test asserting the interpretation renders after a successful analyze (the constitution's "any bug fix/new capability needs a regression test" — here, the regression is "capability shipped but never wired").

**Rationale**: this is the smallest change that satisfies FR-009/US3 using only what already exists and is tested; it matches the audit's own "~1 day, all pieces exist" estimate.

**Alternatives considered**: fetch the full `AssessmentRead` (`GET /assessments/{id}`, which already carries any *cached* `interpretation`/`interpretation_source`, :141-143,158-163) instead of relying on the mutation's own response (rejected as the primary path — it would add a second query for no benefit, since `useInterpretation`'s `onSuccess` already invalidates that query key for anyone else observing it, :90-93 — but worth noting as why a page reload would still show a previously-generated interpretation for free); adding a backend consent re-check to fully close the mid-session-revocation gap (rejected for this feature — contradicts FR-009's explicit "no server-side changes," flagged as a fast-follow instead of silently ignored).

## R6. `validaLabel` consolidation

**Decision**: The true duplicate pair is `lib/insights.ts:107-112` (exported `validaLabel`, already the widely-used one — `InsightsTab.tsx:149`, `AthletesTab.tsx:116`, `InsightsTimeline.tsx` ×5, `HeroLastInsightCard.tsx:104`, `ClubInsightsPage.tsx:100` before its removal) and `AthleteAIAnalysisTab.tsx:89-94`'s private, unexported near-copy (differs only in fallback casing: `"agregado"`/`"resumen de temporada"` vs. `"—"`/`"Resumen de temporada"`). Consolidate: delete the private copy, import the shared `validaLabel` in `AthleteAIAnalysisTab.tsx`, matching casing to the shared version (a one-line visible copy change, acceptable since it's presentation hygiene, not new behavior).

**The other two are not the same kind of duplicate — verified, not merged**:
- `lib/raceCalendar.ts:149-159` (`getValidaLabel`) deliberately renders **roman numerals** ("Válida III") for the calendar surface (matches the CLAUDE.md-documented printed calendar convention), is fully tested with hardcoded expectations (`lib/__tests__/raceCalendar.test.ts:82-95`, e.g. `getValidaLabel(1) === "Válida I"`), and is consumed only by `ComparatorPanel.tsx` (3 call sites). Merging its *output format* into the arabic-numeral `validaLabel` would be a visible convention change belonging to feature 033 (visual coherence), not this cleanup. Left as its own function.
- `MiniSparkline.tsx:37-40` (`romanForValida`, compact "CD"/"Σ"/roman-only badge text) and `InsightsTimeline.tsx:193-196` (`resolveShape`, a shape/icon *classifier* returning `"season-summary"|"departamental"|"normal"`, not a label string) are not label-string duplicates at all — `InsightsTimeline` in fact already imports and uses the shared `validaLabel` for its actual text (`:55,440,450,479,505,600`). Both are small, differently-shaped, single-purpose helpers for space-constrained UI; left unchanged.

**On "retiring the round-99 convention" (FR-006)**: verified that `race_series.kind`/`series_kind` (the feature-014 replacement) is **not** present anywhere in the AI-insights payload types these five helpers read (`insight.valida_num` traces back through `backend/app/schemas/{athlete_race_analysis,race_ai}.py`, part of the separate, actively-evolving `race/ai` LangGraph pipeline which feature 016 explicitly left on the legacy `valida_num` contract, out of scope even for that dedicated fix-it feature). Threading `series_kind` into that pipeline's response schemas would be a real backend change to a different subsystem — out of bounds for a presentation-subtraction feature and inconsistent with spec.md's "no stored-data changes" framing. This feature's achievable, in-scope version of "retiring the convention" is: stop hand-rolling the `=== 99` sentinel in more than one place for the sentence-label format (done, above), and document the surviving numeric check as a single, explicit, commented legacy exception pending a future backend addition — not silently re-duplicate it.

**Alternatives considered**: forcing all five onto one shared function regardless of output-format differences (rejected — would visibly change `ComparatorPanel` and the sparkline/timeline badges, none of which is requested by any FR, and would need new tests for a cosmetic-only, out-of-scope change); threading `series_kind` through the AI-insights backend now (rejected — scope creep into the `race/ai` pipeline, explicitly out of bounds per spec.md and feature 016's own precedent of leaving that contract alone).
