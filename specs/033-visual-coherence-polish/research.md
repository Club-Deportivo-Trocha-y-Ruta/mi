This supersedes 028's illustrative table with the real one.

## R2. A/B/C ordinal presentation

- **Decision**: Render race classes A (full taper)/B (mini-taper)/C (no tapering) as a **one-hue ordinal ramp in the product's own accent hue** (teal, base `--color-primary: #20b7c9`), darkest = most intense (A), lightest = least intense (C) — magnitude reads as depth, per `color-formula.md`'s ordinal rule ("one hue, monotone lightness steps"). Validated (not eyeballed) with the skill's `scripts/validate_palette.js --ordinal` against the app's real white surface (`#ffffff`, not the skill's default `#fcfcfb`):

  | Tier | Hex | OKLCH L | Contrast vs `#ffffff` |
  |---|---|---|---|
  | C — no tapering (lightest) | `#5bc6d5` | 0.77 | 2.00:1 |
  | B — mini-taper (mid) | `#1cb5c7` | 0.71 | 2.48:1 |
  | A — full taper (darkest, most intense) | `#008492` | 0.56 | 4.45:1 |

  `validateOrdinal` report: Lightness monotone **PASS** · Adjacent ΔL **PASS** (≥0.06 both gaps) · Light-end contrast **PASS** (2.00:1, exactly clears the 2:1 ordinal floor) · Single hue **PASS** (spread 0°). Full derivation script output is reproducible; see `data-model.md` for the final table (incl. an optional dark-mode variant, also validated).
- **Rationale**: FR-002 requires A/B/C to read as an ordered intensity scale, never as status colors — using `--color-success/-warning/-danger` for three tapering tiers would violate the color-formula.md collision rule ("status never follows the theme... a status color never impersonates a series") and would visually claim "C = bad," which is false (C is a diagnostic race, not a failure). Anchoring the ramp to the existing brand accent means the ramp reads as "the app's own intensity language" rather than a second, competing palette. The lightest step (C) sits exactly at the ordinal floor (2.00:1) — per FR-002 the letter itself (`A`/`B`/`C`) is always rendered as a visible text label already (not a bare colored dot), so the marginal contrast is mitigated by the mark never being color-alone, consistent with the skill's relief rule.
- **The `"CD"` (Campeonato Departamental) value does not belong to the ordinal ramp.** `lib/insights.ts:145-154`'s `CARRERA_TIER` map treats `"CD"` as a 4th distinct tier value, but per `CLAUDE.md`'s own Copa Valle calendar ("CD 12-jun Ginebra A (full taper 7 days) — Dept. Championship") its *tapering* tier is **A** — the championship-ness is an orthogonal fact, already surfaced correctly elsewhere as a separate trophy badge (`CompetitionDetailPage.tsx:452-460`, amber "CD" pill with a `Trophy` icon, independent of any tapering color). Decision: the ordinal ramp covers exactly 3 steps (A/B/C); `getCarreraTier`'s "CD" case is treated as tier **A** for ramp-coloring purposes, with the existing trophy badge (unchanged) carrying the championship distinction. This is a one-line fix in `getCarreraTier`/`CARRERA_TIER` (return `"A"` instead of the 4th value) with no visual regression to the existing trophy badge.
- **Alternatives considered**: a 4-step ramp including "CD" as its own darkest step (rejected — double-encodes intensity and championship-ness in one channel, and a 4th ordinal step reading darker-than-A would misstate that a championship is *more* intense than a full-taper race, which isn't the claim being made); using the sequential blue from the skill's reference palette instead of the app's own teal (rejected — the app already has a validated, recognized accent; introducing a second blue family purely for this ramp would itself be an inconsistency this feature exists to remove).

## R3. Chart restyle (DistributionChart.tsx, EvolutionChart.tsx)

Full contract in `contracts/chart-style.md`; decisions summarized here with the dataviz rule each one cites.

- **Grid**: keep the existing recessive gray (`rgba(34,42,53,0.08)`, already the right visual weight — matches `--color-border-gray` per `specs/028-frontend-design-foundation/research.md` R5(c)) but **delete `strokeDasharray="3 3"`** at `DistributionChart.tsx:304` and `EvolutionChart.tsx:213`. Cites `anti-patterns.md`: "❌ Dashed gridlines or axis rules... reads as 'projection' or 'threshold'... ✅ solid hairlines." Two-line diff, zero visual redesign otherwise.
- **Axis ink unification**: both charts currently use a **third** gray, `#5a6172` (distinct from `--color-charcoal #2f2f2f` and `--color-mid-gray #717171`), for every tick/axis label (`DistributionChart.tsx:309,315,320,327`; `EvolutionChart.tsx:216,224,228`). Decision: replace with `--color-mid-gray` (`#717171`) everywhere — the token every other secondary-text usage in the app already uses. Cites `marks-and-anatomy.md`: "Text never wears the data color... labels, values, legends, and axis text use text tokens."
- **Color roles** (own series / best / worst), validated as a set against the app's white surface with `pairs:"all"` (any two reference lines can sit adjacent on the same curve):

  ```
  validate(["#20b7c9","#0ca30c","#d03b3b"], {mode:"light", surface:"#ffffff", pairs:"all"})
    [PASS ] Lightness band     — all 3 inside L 0.43–0.77
    [PASS ] Chroma floor       — all 3 >= 0.10
    [PASS ] CVD separation     — worst all-pairs danger↔success ΔE 12.4 (deutan) — clears the ≥12 target
    [WARN ] Contrast vs surface — accent (own series) 2.42:1, below 3:1 — relief required
  ```

  - **Own series (self)** → `--color-primary` (`#20b7c9`, the app's one accent). Replaces **three** different "self" hexes found across the two charts: `DistributionChart.tsx:338`'s area/curve ink `#131316`, its *separate* "Tú" reference-line color `#0ea5e9`/label `#0369a1` (`:345,354`) — i.e. Distribution currently double-encodes "self" with two unrelated blues even before best/worst enter the picture — and `EvolutionChart.tsx:244,246`'s line/dot `#131316`.
  - **Best / worst reference** → `--color-success` (`#0ca30c`) / `--color-danger` (`#d03b3b`). Replaces the ad hoc `#16a34a`/`#15803d` (best) and `#dc2626`/`#b91c1c` (worst) at `DistributionChart.tsx:493-494`. Cites `color-formula.md`'s collision rule: best/worst *mean* good/bad, so they take status tokens, not hand-picked green/red — this was already a status job being done with non-status colors.
  - **Other riders (neither self/best/worst)** → `--color-mid-gray` (`#717171`), replacing `#94a3b8`/`#64748b` (`DistributionChart.tsx:493-494`). Neutral, recedes behind the three meaningful colors.
  - **Contrast WARN on the accent is not dismissable** (skill rule: "obligates a relief channel — visible direct labels or the table view"). This is the concrete reason FR-003's table view is **mandatory**, not a nice-to-have: the own-series line is the one color in this set that doesn't clear 3:1 on white.
- **Championship on-point marking**: today `EvolutionChart.tsx:246` renders every point with an identical `dot={{r:4, fill:"#131316"}}`; the only distinguishing signal is amber text in the legend `<ol>` below (`:263-267`, `entry.series_kind === "championship"`). Decision: custom `dot` render (recharts supports a function/component here) — for the championship point only, a **diamond marker** (rotated-square SVG path, not a new color — championship-ness is identity/occasion, not polarity, so per `color-formula.md`'s "assign color by the job it does" it must not consume a status hue), fill `--color-primary` (it is still the athlete's own point), radius bumped to ~6 (diameter ≥8px per the marker spec `marks-and-anatomy.md`, comfortably clearing the ≥8px/r≥4 floor), with a 2px surface-color ring (the documented "surface ring" mechanism for marks that need to stay legible against a line, `marks-and-anatomy.md` §"The two spacers"). The direct text label ("Cto. Dep.") moves to sit at/above the point itself, in addition to (not instead of) the existing accessible `<ol>` legend below, satisfying FR-003 acceptance scenario 2 ("visually distinct on the data point itself, not only in text below") without removing the already-accessible legend.
- **Reference-label capping**: `RiderReferenceLines` (`DistributionChart.tsx:482-519`) direct-labels every non-self rider — a 10-15 rider category risks `anti-patterns.md`'s "number on every point" failure. Decision: when the category's rider count exceeds **8**, only self/best/worst keep visible direct labels; the remaining riders' reference lines still render (position/density stays informative) but drop their text label. At n≤8 the existing alternating top/bottom placement (`:496-497`) continues to prevent overlap without capping. Cites `marks-and-anatomy.md`: "Label selectively — never a number on every point... label the endpoint, the extreme, or the one series the story is about."
- **Table-view twin**: FR-003 requires "a table view available for the main chart data." Given the accent's contrast WARN applies identically to both charts' own-series line, the twin applies to **both**: Distribution generalizes the existing `LowConfidenceTable` (`DistributionChart.tsx:399-463` — already the exact right shape: position/name/time, self-row highlighted) into the shared table view for the n≥5 path too, behind a "Gráfica/Tabla" toggle built on the already-installed `ui/tabs.tsx` (no new dependency); Evolution gets an equivalent table (event label/date/value, mirroring the fields its own tooltip already shows, `EvolutionChart.tsx:321-341`). The existing `n<5`/`n<3` low-confidence fallbacks are **preserved as-is** (already the right pattern per the skill's "is it even a chart?" heuristic) — the toggle only appears once there's a chart to toggle away from.
- **Not touched here**: the inline `cardShadow` constant duplicated in both files is swept by 028's shadow-token consolidation (`specs/028-frontend-design-foundation/research.md` R5(a)), not re-specified in this feature to avoid duplicate ownership.
- **Alternatives considered**: coloring the championship point with a 5th ad hoc color (rejected — collision rule again, and a 4th/5th hue would need its own CVD re-validation against the other three); capping reference labels at a fixed count like "top 3" regardless of field size (rejected — the task's own hint and the anti-pattern are about *density*, not a fixed cardinality; the >8 threshold matches the field sizes actually seen in the app, 10-15 riders per report 04).

## R6. Proactive AI budget/wait

- **What exists today (backend)**:
  - **Budget**: `settings.race_ai_budget_usd_30d` (default `$20`, `backend/app/config.py:126`), enforced by `check_budget()` (`backend/app/services/race/ai/budget_guard.py:197-238`), which sums `athlete_ai_insights.metrics_snapshot_json→cost_usd_total` over a rolling 30-day window (`_sum_cost_last_30d`, `:117-139`) and raises `BudgetExceededError` when spend ≥ budget. Both athlete-launch (`athlete_race_analysis.py:602-611`) and season-summary (`:862-873`) endpoints catch it and return **503** with a dollar-figure message — today's *only* signal, and only after the click.
  - **Concurrency**: a module-global semaphore, `MAX_CONCURRENT_RUNS = 10` (`backend/app/services/race/ai/runner.py:43-44`), with pure, already-existing read helpers `get_active_run_count()` and `has_capacity()` (`:70-78`, no DB access, free to call). Exceeding it raises `RunBackpressureError` → **429** (`athlete_race_analysis.py:708-725`; also `race_analysis.py`, `group_launch.py:567`).
  - **Latency**: `GET /admin/ai-usage` (`race_analysis.py:1268-1280`, admin-only via `_admin_only`, `:116`) already computes `latency_ms_p50`/`p95` and `cost_usd_total` from the same `athlete_ai_insights` table, over a configurable window. `AIHealthPage.tsx`/`app/routers/ai.py:131-139`'s `/api/ai/health` is a **different**, simpler admin-only endpoint (enabled/provider/model only — no budget or latency).
  - **Nothing coach-facing exists.** The coach only ever sees the 503/429 message *after* clicking launch (`AnalyzeAthleteButton.tsx:34-37`, `GroupAnalysisPanel.tsx:42-61`), despite the ETA machinery (`estimated_seconds_remaining`, `AnalysisRunTimeline.tsx:301,333-336`) already existing for **in-flight** runs — it says nothing pre-launch.
- **Decision: smallest honest solution is a new coach-safe read endpoint**, `GET /api/ai/status`, **not** a client-side derivation. Rationale for rejecting the client-side option: `AnalysisRunTimeline`'s node-duration data is only available *while a run is active* (or after, if cached client-side across sessions, which nothing does today) — there is no pre-launch client-side signal to derive an ETA from without inventing new client storage; and budget state is a server-side dollar sum the client cannot see at all (no endpoint exposes it to non-admins today). A tiny new endpoint is honest, cheap (reuses existing queries verbatim), and RBAC'd correctly on the first try.
- **Response shape** (contract in `contracts/ai-identity.md`, styled like `specs/028-frontend-design-foundation/contracts/newsletter-status-summary.md`):
  ```json
  { "budget_status": "ok", "budget_remaining_pct": 62, "concurrency_available": true, "est_wait_seconds": 24 }
  ```
  - **`budget_remaining_pct`, not `analyses_remaining`.** Decision made explicitly against the alternative named in the task: "N analyses remaining" would require assuming an average cost-per-analysis that varies by prompt length/provider and can mislead (a coach could see "3 remaining" and have the very next analysis exceed the true remaining budget). A percentage of the same rolling-30-day sum the hard-block already uses is honest and can't overpromise.
  - **`est_wait_seconds`** is the *typical total analysis duration* (the "~20-30s" hint report 04 recommends), not a queueing delay — reuses the same `latency_ms_p50` computation `/admin/ai-usage` already does over a short recent window, converted to seconds. It is not a promise, just a recent-typical figure — copy will hedge with "≈" per existing ETA copy conventions (`AnalysisRunTimeline.tsx:333-336` already says "≈ Ns restantes").
  - **`concurrency_available`** is a direct boolean read of `has_capacity()` — free, in-memory, no query.
  - **`budget_status`**: `"ok" | "warning" | "exhausted"` derived server-side from the same threshold the hard-block already uses (`exhausted` when `budget_remaining_pct <= 0`, matching `check_budget`'s `current >= max_cost_usd_30d`) plus an `80%`-used `warning` band the frontend can use for an amber hint before the hard block. This keeps the disable/enable decision (FR-006: "exhausted budget... MUST disable launch") server-computed and consistent with the actual enforcement, not re-derived client-side from a raw percentage with its own threshold that could drift out of sync.
- **RBAC**: `require_role([UserRole.coach, UserRole.admin])` — the exact `_coach_or_admin` dependency already defined at `race_analysis.py:115`, reused rather than duplicated.
- **Performance**: reuses `_sum_cost_last_30d`'s existing indexed aggregate (already run on every launch attempt today) plus an in-memory semaphore read — trivially inside Constitution IV's p95 ≤ 500ms budget for cached/warm reads.
- **Failure path unchanged**: FR-006 keeps 503/429 as the *execution-time* re-validation (budget/concurrency can change between the hint being shown and the click); the new endpoint is purely a pre-launch hint, never a gate by itself.
- **Alternatives considered**: exposing raw dollar amounts to the coach (rejected — `/admin/ai-usage`'s dollar figures stay admin-only by existing convention; a percentage is the coach-safe subset the task brief asks for); computing `est_wait_seconds` from a live in-memory rolling average updated per completed run instead of the DB (rejected — `_sum_cost_last_30d`'s query pattern already exists, is already proven fast enough to run on every launch, and avoids a second source of truth for "recent performance").

## R7. Dark mode (optional story, FR-008)

- **Decision**: ship `@custom-variant dark (&:where([data-theme=dark], [data-theme=dark] *))` exactly as verified for Tailwind v4 in `specs/028-frontend-design-foundation/research.md` R5, scoped to **coach surfaces only** (parent portal routes are out of scope — this program is coach-experience-specific throughout). Token mapping (all dark values newly derived and contrast-checked against the app's real dark surface `#1a1a1a`, not eyeballed):

  | Role | Light (today) | Dark (new) | Contrast vs dark surface |
  |---|---|---|---|
  | Page plane | implicit white | `#0d0d0d` | — |
  | Card/chart surface | `#ffffff` | `#1a1a1a` | — |
  | Primary text (`--color-charcoal`) | `#2f2f2f` | `#f2f2f0` | 15.53:1 |
  | Secondary text (`--color-mid-gray`) | `#717171` | `#a3a3a3` | 6.90:1 (exceeds light mode's own 4.88:1) |
  | Disclaimer text (`--color-text-disclaimer`) | `#5a5a5a` | `#b8b8b8` | 8.77:1 |
  | Subtle panel fill (`--color-light-gray`) | `#f5f5f5` | `#242424` | — (fill, not text) |
  | Border (`--color-border-gray`) | `rgba(34,42,53,0.08)` | `rgba(255,255,255,0.10)` | — |
  | Card shadow | `--shadow-card` (dark rgba shadow) | replaced by a 1px `rgba(255,255,255,0.08)` ring — shadows don't read against an already-dark surface | — |
  | Accent (`--color-primary`) | `#20b7c9` | **unchanged** | 7.19:1 (light mode was 2.42:1 — needed the chart relief channel; dark mode needs none) |
  | Status success/warning/danger | `#0ca30c`/`#fab219`/`#d03b3b` | **unchanged** | 5.19 / 9.49 / 3.62 |
- **A pleasant asymmetry, worth stating**: the accent and all three status tokens need **zero** hex changes between modes — every one already clears an adequate contrast on the dark surface as-is (verified above). Only surface/text/border/shadow tokens need new dark values. This matches the earlier audit's framing ("cheaper than most apps thanks to the monochrome base") with actual numbers behind it now.
- **Activation mechanism — decision: both.** Default follows `prefers-color-scheme: dark` (CSS-only, `@media` block scoped to `:root:not([data-theme])` so it only applies absent an explicit choice); a manual override lives in the user menu (030's shell) as a 3-state control (Sistema/Claro/Oscuro), persisted to `localStorage` (`tyr:theme-preference:v1`), applied by setting `data-theme="dark"|"light"` on `<html>` — removing the attribute falls back to the media query. This is the standard "system default, explicit override wins" pattern and matches how the `@custom-variant` selector is written (it targets the attribute; the media query is the fallback path when no attribute is set).
- **Dependency**: strictly requires 028's shadow/token consolidation to be merged first (inline `boxShadow` styles cannot respond to `prefers-color-scheme` or the `data-theme` attribute) — already called out as a hard sequencing dependency in the spec's Assumptions and in `docs/17-coach-ux-redesign/proposal.md` §8.
- **Alternatives considered**: auto-only (no manual override) — rejected, a coach whose OS is dark but who wants light while planning outdoors (or vice versa) has no escape hatch, and 030 already builds the user-menu real estate this control needs; system-only detection via JS instead of CSS media query (rejected — CSS-only is simpler, no flash-of-wrong-theme risk).

## R8. Keyboard shortcuts (optional story, FR-009)

- **Decision**: a minimal, discoverable set that **reuses** 030's already-defined areas and controls rather than inventing a parallel navigation model:

  | Shortcut | Action |
  |---|---|
  | `g` then `i` | Jump to Inicio |
  | `g` then `e` | Jump to Entrenamiento (Calendario default) |
  | `g` then `c` | Jump to Competencias |
  | `g` then `a` | Jump to Atletas (coach-only) |
  | `g` then `f` | Jump to Familias |
  | `g` then `b` | Jump to Biblioteca |
  | `n` | Open the existing quick-create control (030 `FR-006` — new session/competition/calendar event/athlete, role-filtered) |
  | `?` | Open a "Atajos de teclado" help dialog listing the above |

  Area letters are the six groups 030 defines (`specs/030-coach-navigation-redesign/spec.md:15,93`: Inicio, Entrenamiento, Competencias, Atletas, Familias, Biblioteca) — no new information architecture invented. `n` opens the *same* quick-create menu 030 ships, keyboard-triggered rather than duplicated.
- **Discoverability**: a "Atajos de teclado ⌨" entry in the user menu (030 already builds a user menu, `FR-006`) opens a plain `ui/dialog.tsx` (already installed) listing the table above — no new UI chrome, no new dependency.
- **Guardrails**: shortcuts are inactive whenever `document.activeElement` is an `<input>`/`<textarea>`/`contenteditable`, or a modal/sheet is open — standard practice, prevents hijacking normal typing (RHF forms, the chat panel, rubric notes, etc.).
- **Explicitly excluded**: a command palette (program decision D5, reaffirmed in this spec's Assumptions and `specs/030-coach-navigation-redesign/spec.md:125`) — grouped navigation + quick-create already solves discoverability at the current route count; shortcuts here are a keyboard-only accelerant on top of that, not a search surface.
- **Dependency**: requires 030's six-area grouping and quick-create control to exist first (sequencing, consistent with the overall program order 028→…→033).
- **Alternatives considered**: single-key shortcuts without the `g` prefix (rejected — collides with normal typing far more often, e.g. `a` alone inside any text field, whereas a two-key chord is the standard mitigation, e.g. GitHub/Gmail-style); adding search-by-name shortcuts (rejected — that is the command palette in disguise, out of scope by D5).
