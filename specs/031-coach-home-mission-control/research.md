## R0. Dataviz skill applied — headline decisions

The skill was loaded before any tile/meter design work, per its procedure (form → color → validate → marks → interaction → accessibility). Three decisions it drives directly:

1. **Form choice, not a chart.** Per `choosing-a-form.md`'s "Is it even a chart?" table: a single current value → **stat tile** ("Próxima sesión", "Próxima carrera"); a single ratio against a limit → **meter**, same-ramp track ("Carga semanal"), never a gauge/donut. The pending-work list is a **to-do list** (rows with counts + links), not a KPI row — counts here are actionable inbox items, not headline metrics, so they get list-row treatment, not `StatCard` treatment. This matches `docs/17-coach-ux-redesign/agent-reports/04-product-design-modern-patterns.md:110-130`'s proposal, which this spec formalizes.
2. **Meter anatomy is a literal same-hue pairing per state, not a fixed gray track.** `marks-and-anatomy.md:74-76`: "the fill carries severity (accent → warning → danger); the unfilled track is a lighter step of the **same ramp** (blue-on-blue, etc.)." Read literally, the parenthetical example ("blue-on-blue") means the track always matches whichever hue is currently active in the fill — comfortable = teal fill / pale-teal track, near-cap = amber fill / pale-amber track, over-cap = red fill / pale-red track — not a neutral gray track throughout. See R6 for the full state table and the reasoning for using **accent** (not "success green") at the comfortable end.
3. **Value-leads hierarchy** (`marks-and-anatomy.md`'s stat-tile contract, `label · value · delta · trend`): every tile and the meter render the number first/largest (Sans semibold, proportional figures — never `tabular-nums` on a lone headline value per the skill's figures rule) with the label as a smaller caption, never the reverse. Applied to all three hero tiles and both meter rows in `contracts/home-tiles.md`.

No new chart library is introduced (see Constitution Check in `plan.md`): the meter is plain divs/CSS, matching the skill's own build-in-plain-HTML method (`components.md`: "Meter / progress track — same-ramp tracks" is a Tier-1 piece assembled from Tier-0 color roles, not a charting-library primitive).

## R2. Aggregate endpoint(s) — one endpoint, deliberately narrow scope

**Decision**: **One** new read-only endpoint, `GET /api/dashboard/coach-summary`, returning **exactly** `consents_pending`, `insights_stale`, and `weekly_load` — the three items with no existing home. It deliberately does **not** re-fetch `results_to_import`, `activities_unlinked`, or `newsletters_due` (those stay on their existing/reused sources per R1).

**Rationale**:
- **Cold start.** Render free-tier wakes in ~50 s (CLAUDE.md); fewer *new* round trips during warm-up is better, but the fewest-total-requests outcome is achieved by **not duplicating** data the page fetches anyway, not by centralizing everything into one call. Folding `results_to_import` into the new endpoint would mean fetching the season's race events **twice** (once via `useRaceEventsList` for the hero race tile's name/date/place, again inside the new aggregate for the count) — a real double-fetch of the same underlying rows on every landing. Composing the count client-side from the tile's own already-fetched data costs zero extra requests.
- **Independent availability.** `backend/app/main.py:97-110` mounts the entire activities/Strava router **conditionally** on `settings.strava_enabled`. If a club runs with Strava disabled, `GET /api/activities` isn't mounted at all (404). Keeping `activities_unlinked` on its own request means only that one row degrades (per FR-004) when Strava is off — bundling it into `coach-summary` would mean either the whole aggregate 500s/omits a field pointlessly tied to an unrelated subsystem's availability, or the dashboard service takes on a conditional import of the Strava models it otherwise has no reason to touch.
- **Cacheability.** The three new fields share one staleness profile (club-wide operational counts that change on the order of hours, not real-time) and one RBAC gate, so one `staleTime`/one query key is the right grain — see R8. Splitting them into three tiny endpoints would triple the request count for data that is cheap to compute together (all three queries are scoped to the same club's small athlete roster) with no independent-availability benefit (unlike the activities case above, none of `consents_pending`/`insights_stale`/`weekly_load` depend on an optionally-disabled subsystem).
- **Constitution IV (p95 ≤ 500 ms, no N+1).** All three sub-queries are bounded by **club roster size** (~20-40 athletes for this club), not by global table size — see R3–R5 for each query shape. None fan out per-athlete requests; each is one grouped/joined query. Documented in `contracts/coach-summary-endpoint.md`.
- **RBAC.** Same `require_role([UserRole.admin, UserRole.coach])` gate as `alerts.py:41` — one gate for one endpoint, not three copies.
- **Graceful degradation (FR-004).** Each of the three fields is computed independently server-side (own try/except, see contract) so a failure in one sub-query nulls only that field in the response rather than 500ing the whole payload — satisfying "the list must render without them (no errors)" without needing three separate HTTP failure domains.

**Alternative considered and rejected**: a single mega-endpoint carrying all five pending counts + weekly load (the literal reading of the spec's Key Entities note, "up to three summaries," left open). Rejected for the double-fetch and independent-availability reasons above — it would make the "existing data" tiles (which the spec's Assumptions section explicitly wants to ship in the **first** increment, before any backend work) implicitly depend on the new endpoint for their counts, coupling two independently-shippable increments.

**Alternative considered and rejected**: three separate tiny endpoints (`/consents-summary`, `/insights-stale-summary`, `/weekly-load`). Rejected — no independent-availability benefit between these three (unlike activities/Strava), so three round trips only adds cold-start latency and three RBAC/test surfaces for no isolation gain.

**Net effect on request count**: the landing page issues exactly 6 fixed-shape requests regardless of club size — `useAlerts` (existing), `useTrainingSessions` (existing), `useRaceEventsList` (existing, serves 2 tiles), activities count-only (existing endpoint, new param combination), newsletter summary (028, reused), and the one new `useCoachSummary`. This satisfies SC-005 or FR-008's "request count independent of club size."

## R3. Weekly load calculation

**Rule (CLAUDE.md non-negotiable #4): "Weekly hours ≤ athlete age."** This is stated per-athlete; the meter reports **per age band** (10-12, 13-15 — the same bands CLAUDE.md's "Age group differentiation" section already uses), so a banding rule is required to turn a per-athlete ceiling into a per-band ceiling.

**Age-band bucketing**: `age_decimal = compute_age_decimal(athlete.birth_date)` (`backend/app/services/category.py:6-11`, already used by `alerts.py:92`). Band = `"10-12"` when `10 ≤ age_decimal < 13`; `"13-15"` when `13 ≤ age_decimal < 16`. Athletes outside `[10, 16)` are excluded from both bands (the club's target population is 10-15 per CLAUDE.md; out-of-range rows are a rare edge case, not silently mis-bucketed).

**Cap per band — decision**: use the **band's minimum age** in hours, converted to minutes (10-12 → 10 h = 600 min; 13-15 → 13 h = 780 min). **Rationale**: the alternative (an average or max age actually present this week) is dynamic and could understate risk for the youngest athlete in the band — e.g. if the band's average age is 11.5 and the cap is set there, a 10-year-old training 11 h/week would read "comfortable" while already 1 h over their own personal ceiling. A fixed, conservative per-band floor protects the youngest/most vulnerable athlete in the band at the cost of occasionally flagging "near-cap" for a band whose actual mix skews older — an acceptable trade for an **advisory** (never blocking, per FR-005/spec US3 acceptance #2) tile. A true per-athlete sum (join through attendance, compare against each athlete's own age) was considered and rejected as disproportionate build cost for a glance-level landing meter — the coach still makes the real call per-session; this tile is a headline warning light, not a scheduling engine.

**Attribution (which sessions count toward which band)**: `SessionAttendance` rows are created **at session-creation time** for every convocado (`backend/app/services/training/sessions.py:144-152` — status starts `AUSENTE` as a placeholder, corrected at execution), so a **planned** session's roster is already queryable before it happens. A planned session's `duration_min` is attributed to a band if **any** convocado falls in that band. A joint session spanning both bands counts its full duration toward **both** bands' totals — each band's athletes really experienced that session's duration, so this is not double-counting in the sense the term usually warns against; it would be a bug only if a single band's sum counted the same session twice, which the query prevents via `DISTINCT` on `(session_id, band)` before summing.

Query shape (one grouped read, no N+1 — bounded by this week's session/roster count, not global table size):
```sql
SELECT band, SUM(duration_min) FROM (
  SELECT DISTINCT ts.id AS session_id, ts.duration_min, <age_band_expr> AS band
  FROM training_sessions ts
  JOIN session_attendances sa ON sa.session_id = ts.id
  JOIN athletes a ON a.id = sa.athlete_id
  WHERE ts.status = 'planned'
    AND ts.club_id = :club_id
    AND ts.scheduled_date BETWEEN :week_start AND :week_end
) sub
GROUP BY band
```

**Week bounds — club timezone**: `scheduled_date` is a plain `DATE` column representing the club's local calendar date directly (no UTC conversion, unlike the `DateTime` columns — see `lib/datetime.ts:6-13`'s documented naive-UTC convention for those). The ISO week (Monday–Sunday) must be computed from **"today" in `America/Bogota`**, not the container's local date — the backend already uses `ZoneInfo("America/Bogota")` as an inline literal in 17 files (e.g. `backend/app/services/calendar/birthdays.py:107`), so this feature follows the same established idiom rather than introducing a shared constant (no existing backend constant to reuse; introducing one is an out-of-scope nice-to-have, noted but not required). Using naive `date.today()` would be wrong specifically in the evening Bogotá window (UTC−5) where the container's UTC clock has already rolled to the next day.

## R4. Consents-pending aggregate

**Decision**: reuse the *exact* single-athlete semantics already used by the parent-facing endpoint, vectorized across the roster, rather than inventing a new consent-state taxonomy. `get_current_consent_for_athlete` (`backend/app/services/privacy.py:63-83`) defines "vigente" (current) as the most recent `ParentalConsent` row **with `withdrawn_at IS NULL`**. An athlete is **pending** when no such row exists on the **active policy version** (`get_active_policy`, `privacy.py:34-47`). This is computed as: club athlete count minus `COUNT(DISTINCT athlete_id)` from `parental_consents` where `withdrawn_at IS NULL AND policy_id = :active_policy_id`, scoped to the club's athlete ids — two small queries (resolve active policy, then one grouped count), no per-athlete fan-out.

Note: this is **not** the same 4-way state (`current`/`outdated`/`revoked`/`never`) `ConsentStatusPanel.tsx:45-50`'s `getConsentState` displays to parents — that panel's `revoked` branch is fed by `AthleteConsentStatus.current_consent`, which (per `get_consent_status`, `privacy.py:142-169`, calling `get_current_consent_for_athlete`) can only ever be non-null with `withdrawn_at == null`, so its `revoked` case is unreachable through today's data path. This aggregate does not attempt to reproduce or fix that discrepancy (out of scope for this feature — it is a pre-existing frontend/backend semantic mismatch in a different component); it defines its own precise "pending" predicate directly against the model, matching only the proven single-athlete rule.

## R5. Insights-stale aggregate

**Decision**: count athletes (in the coach's club) whose currently-**active** insight (`athlete_ai_insights.is_active = 1` — the sentinel described in `backend/app/models/athlete_ai_insight.py:12-15`) is generated from a run marked stale (`agent_runs.stale_since IS NOT NULL`, joined via `athlete_ai_insights.agent_run_id = agent_runs.id`). This mirrors exactly what the per-athlete `stale_run_id` field already exposes (`frontend/src/types/athleteRaceAnalysis.types.ts:274-281`: "presente solo cuando el run del que proviene el insight fue marcado como desactualizado") — this aggregate is the count of athletes for whom that field would be non-null, club-wide, without fetching every athlete's insight individually.

Query is one join (`athlete_ai_insights` ⋈ `agent_runs`) filtered to the club's athlete ids (`ix_agent_runs_athlete_started` and the insight table's existing indexes make this cheap at club-roster scale; no new index is required because the filter is bounded by `athlete_id IN (...)` over ~20-40 rows, not a global scan — noted in the contract as a scale assumption, revisit only if the product becomes multi-club-at-scale).

## R6. Meter presentation (dataviz skill applied)

Per R0.2, each state is a **{fill, track}** pair from the same hue, not a fixed gray track:

| State | Threshold (of band cap) | Fill | Track |
|---|---|---|---|
| Comfortable | ≤ 80% | `--color-primary` (teal accent) | pale tint of `--color-primary` |
| Near-cap | > 80% and ≤ 100% | `--color-warning` (`#fab219`) | pale tint of `--color-warning` |
| Over-cap | > 100% | `--color-danger` (`#d03b3b`) | pale tint of `--color-danger` |

**Why "accent," not "success green," at the comfortable end**: the skill's literal meter spec (`marks-and-anatomy.md:74-76`) reads "the fill carries severity (**accent** → warning → danger)" with the worked example "(blue-on-blue, etc.)" — a three-step escalation starting from the brand accent, not the four-step status scale (good/warning/serious/critical) `StatusBadge` uses elsewhere. This is a deliberate distinction, not an inconsistency: "comfortable load" is a neutral-normal state (plenty of room), not an achievement/completion (what green usually signals in this app's own semantics, Constitution III: "green = success/complete"). Reusing status-green here would risk being misread as "session complete" rather than "safe amount of training planned." The 80% threshold (rather than exactly 100%) is a deliberate early-warning margin consistent with the feature's "advisory, process-framed, never alarmist" requirement (US3 acceptance #2) — it gives the coach a heads-up band before the hard, non-negotiable ceiling is actually crossed.

**Pale tints**: no pre-existing light-tint tokens for `--color-primary`/`--color-warning`/`--color-danger` exist in `style.css` today. Recommend `color-mix(in oklch, var(--color-X) 18%, white)` at render time (Tailwind v4 + modern browsers already assumed for this tablet-first coach product) over minting three new static tokens — avoids permanently growing the token set for a single component, and the ratio (18%) is a starting point for visual QA, not a hard contract value.

**Two independent meters, not one shared-axis chart**: per the skill's non-negotiable "One axis… two measures of different scale → two charts… indexed to a common base," the 10-12 and 13-15 bands have **different caps** (600 vs. 780 min) — a single bar chart plotting both bands' absolute minutes on one shared axis would make "how close to cap" illegible (a taller bar isn't necessarily closer to *its own* limit). Two small-multiple meters, each independently normalized to 0–100% of its own cap, is the correct application of "index to a common base" (the common base being *percent of own cap*, not absolute minutes).

**Over-cap rendering**: the bar itself cannot exceed 100% of its own width sensibly; when `planned_minutes > cap_minutes` the fill renders full-width in the danger hue and the value-leads numeric readout communicates the actual overage in text (e.g. "630 min planificados · tope 600 min (10-12 años)"), never an overflowing/clipped bar. See `contracts/home-tiles.md` for exact copy.

**Value-leads hierarchy applied**: each meter shows, in this order: (1) the bold headline value ("X min planificados" or a hh:mm-style figure — proportional figures, not `tabular-nums`, per the skill's figures rule for standalone display values), (2) a smaller caption naming the band and its cap, (3) the bar, (4) a link to the sessions involved. Same order applied to the two hero stat tiles (session/race name is the value; countdown and place are captions).

**Status colors reused, not reinvented**: `--color-success/-warning/-danger` are already registered as 028's planned token additions (`specs/028-frontend-design-foundation/research.md` R5(d)), themselves sourced "from the validated dataviz status scale" — i.e., 028 already adopted this skill's exact validated hex values (`#0ca30c`/`#fab219`/`#d03b3b`, matching `references/palette.md`'s Status palette table). This feature consumes `--color-warning`/`--color-danger` as-is; it does not reuse `--color-success` for the meter (R0.2/above), but continues to use it for the discrete `StatusBadge`-style states elsewhere on the page (e.g., an "al día" style badge, if any) where "success" genuinely means completion.

**Table/text fallback**: per the skill's "Is it even a chart?" table, a meter already **is** the minimal form (not a chart needing a table twin) — there is no lower-tier fallback to design. When `weekly_load` is entirely absent (aggregate unavailable), the row/tile is omitted per FR-005 acceptance #3, not replaced by a text table (would contradict "never blocking the rest of the home").

## R7. Stat-tile presentation (hero tiles)

Both hero tiles (`StatCard` + additive slots per 028's contract) follow the figure contract: `label` (sentence case, no trailing colon), `value` (session/race name, semibold), `hint` (the countdown/date/place), and — new, additive to 028's `StatCardProps` — a `tone`/`urgency` slot driving a left accent or badge for the race tile's taper-window state. This is documented as an **additive** extension (028's consumption map explicitly says "031 home consumes `StatCard` (+ additive slots)"), not a redefinition of the existing `label/value/hint/isLoading/href` props.

**Taper urgency mapping** (from CLAUDE.md's Copa Valle calendar + the already-encoded `CARRERA_TIER` map, `lib/insights.ts:145-154`, and the exact copy strings already used for A/B/C in `frontend/src/components/calendar/EventForm.tsx:71-75`): A → "Tapering completo (5-7 días)"; B → "Mini-tapering (3-4 días)"; C → "Diagnóstica — sin tapering"; CD (Campeonato Departamental) → same taper discipline as A ("Tapering completo — Campeonato Departamental," per CLAUDE.md's calendar row "CD 12-jun Ginebra A (tapering completo 7 días)"). Urgency escalates (neutral → warning-accent → danger-accent) as `days_remaining` crosses into the tier's taper window (5-7 d for A/CD, 3-4 d for B, never for C) — full thresholds in `contracts/home-tiles.md`.

## R8. Refresh semantics

**Global defaults** (`frontend/src/App.tsx:179-191`): `staleTime: 5 min`, `gcTime: 24 h`, `retry: 3` exponential backoff, `refetchOnWindowFocus` left at the TanStack v5 default (**true**, not overridden anywhere in the app).

**Decision for `useCoachSummary`**: override `staleTime` down to **60 s** (pending-work counts are more action-oriented/volatile than most cached reads, but still not so cheap to compute that sub-minute polling is warranted) and set `refetchOnMount: "always"`. **Rationale**: the realistic flow is land on Inicio → tap a pending row → resolve it on another screen → navigate back to Inicio (a full route mount, since `DashboardPage` unmounts on navigate-away in this router setup) — `refetchOnMount: "always"` guarantees the counts are current on that return regardless of the 60 s window, directly satisfying FR-008 ("MUST refresh counts when the coach returns to the home") and the "concurrent resolution... refetch on focus/return" edge case, without touching any of the five unrelated mutations that resolve each item. `refetchOnWindowFocus: true` (already the app default) covers the same-tab-different-window case for free.

**Alternative rejected**: wiring explicit cache invalidation of `["dashboard","coach-summary"]` into every resolving mutation (import commit, activity link, newsletter send/generate, consent renew, stale-run re-execute). Rejected — five touch points across unrelated features for the same effect `refetchOnMount` gives for free, and it would mean editing modules this feature has no other reason to touch (scope creep against the spec's stated boundary: "no changes to AI pipelines... or stored data").

The two reused/existing sources keep their own hooks' existing staleness behavior unchanged (`useRaceEventsList`/`useTrainingSessions` already set 5 min/default respectively) — this feature does not tune them.

## R9. Cold start, skeletons, and the persistence allow-list

**Skeletons**: `ui/skeleton.tsx` (the shadcn `Skeleton` primitive) already exists and is reused as-is — no new primitive needed. `ErrorState`'s `isColdStart` variant (028, not yet implemented in code — see Assumptions in `plan.md`) is the contract this feature builds against for the rare true-error path; skeletons (not `ErrorState`) are what render during the ~50 s warm-up window per FR-008/edge case.

**A materially relevant, code-confirmed detail**: `frontend/src/lib/persistAllowList.ts` is a **default-deny** registry (feature 012) gating which TanStack Query entries may be written to `localStorage` for instant-return-visit rendering. Checking each of this feature's query keys against it:

- `["raceEvents", ...]` is **already allow-listed** (`persistAllowList.ts:56`) — confirmed safe for minor PII ("Race-event metadata: list + detail (name/date/location/conditions). No names."). The "Próxima carrera" tile **and** the "resultados por importar" row (both riding on this query) therefore render instantly from device cache on a cold start / return visit, before the live refetch resolves.
- `["training-sessions", ...]` is **explicitly excluded** (`persistAllowList.ts:24-27`, "list items expose `media[].athlete_ids` and free-text `coach_notes`"). The "Próxima sesión" tile therefore shows a skeleton on cold start / cleared cache — this is correct, pre-existing privacy behavior, not a gap this feature should try to close.
- The activities count-only request is **not** allow-listed today, and must **stay** that way even though this feature only reads `.total`: with `page_size=1` the response body still contains one full `ActivityOut` row including `athlete_name` (`frontend/src/types/strava.types.ts:77`) — persisting that response to disk would leak one minor's name regardless of which field the UI happens to render. The "actividades sin enlazar" row shows a skeleton on cold start, same as the sessions tile.
- The new `["dashboard", "coach-summary"]` query is a **good candidate to add** to the allow-list: its payload is exactly counts and per-band minute sums, no names, no ids beyond the club's own athlete PKs used server-side only — i.e., it is already the kind of "counts only" shape the feature's own privacy requirement (FR-010) mandates. Recommended as part of this feature's implementation (with the `data-privacy-guard` review the file's header requires for any new prefix), so the weekly-load meter and the two new inbox rows also render instantly on cold start.
- The 028 newsletter-summary key is not this feature's to allow-list (028's scope), but is noted here for cross-feature awareness: its contract already states "No athlete names or PII in the payload (IDs only...)," so it would be an equally reasonable future addition — left to 028.

This turns "the home must never error during warm-up" into a mostly-solved problem for 3 of 5 rows/tiles (race tile, results-to-import row, and — once added — the meter + 2 new inbox rows) via existing/likely allow-listing, with skeletons as the correct, deliberate behavior for the remaining 2 (session tile, activities row) rather than a gap to close.

## R10. Privacy

FR-010 requires the landing to show no minor's sensitive data beyond what `MeasurementAlerts` already shows (unchanged). Verified for the new endpoint: `consents_pending` and `insights_stale` are bare integers; `weekly_load` entries are `{age_band, planned_minutes, cap_minutes}` — no athlete ids, names, or session content. This satisfies Constitution's Quality Gates ("no name, DOB, medical detail... in logs... or any... response") for the one new payload this feature introduces. Structured logs for the new endpoint follow the existing convention (ids/counts only, e.g. `run_staleness.py:138-143`'s `logger.info(...)` with only numeric ids/counts, never names).

## R11. Admin variant

`ProtectedRoute` already allows both `admin` and `coach` on `/dashboard` (`frontend/src/App.tsx:256-263`) — no routing change needed.
