## R1. Backend gap analysis — technique (THE finding)

**Decision**: No endpoint today lets a coach attach technique exercises to an **existing** training session. A new endpoint is required: `POST /api/technique/sessions/{training_session_id}/exercises`, added as a sibling to the existing `GET` at the identical path.

**Evidence**:
- `backend/app/routers/technique.py:343-384` — `POST /api/technique/sessions` (`assemble_session`) always creates a **brand-new** `TrainingSession` (docstring: "Crea una sesión de entrenamiento ordinaria vía `training_svc.create_session` y guarda los ejercicios de técnica"). It is the only write path into `TechniqueSessionExercise`.
- `backend/app/services/technique/assembler.py:259-522` (`assemble_technique_session`) — the CREATE path (lines 419-522) calls `training_create_session` (imported at line 440) exactly once and then inserts link rows. The RE-EDIT path (lines 345-417, keyed on `combined_exercise_id`, the gymkhana-composer synthetic exercise) does *not* create a new session, but it **replaces** all `TechniqueSessionExercise` rows for that session (delete-then-reinsert, lines 357-387) and is only reachable when re-opening the composer for a *specific* synthetic exercise — it is not a general "attach more items to any session" path, and the composer itself is slated for removal by spec 029.
- `backend/app/routers/technique.py:392-409` — `GET /api/technique/sessions/{training_session_id}/exercises` is read-only.
- Confirmed no other technique write route exists: the router inventory docstring (`technique.py:11-24`) lists exactly the 9 routes above and curation routes (`POST/PUT/PATCH /exercises*`), none of which touch an existing session's link rows outside the two paths above.
- Frontend confirms the gap is real today, not latent: `frontend/src/routes/technique/SessionBuilderPage.tsx` is still routed at `/technique/sessions/new` (`frontend/src/App.tsx:706,716`) and still calls `assembleSession` → `POST /api/technique/sessions` (`frontend/src/api/technique.ts:69-75`, `frontend/src/hooks/technique/useTechnique.ts:103-108`). Spec 029 (not yet implemented — this file still exists unmodified) will delete this screen; 032 must not depend on it surviving.

**Rationale for the new endpoint's shape**:
- Path chosen as a sibling of the existing `GET` (same router file, same resource) rather than a new path under `/api/training-sessions/...` (the session-CRUD router, `backend/app/main.py:80`, prefix `/api/training-sessions`) because `TechniqueSessionExercise` is owned and validated by `technique.py`/`assembler.py`, exactly mirroring how strength's attach endpoint lives in `strength.py` (not in the session router) and interval structures' create lives in `intervals.py`.
- Reuses the existing `AssembleItem` schema (`backend/app/schemas/technique.py:360-365`: `exercise_id`, `segment`, `position`) for the request body — no new item shape needed.
- Reuses `_load_exercises_by_ids` (`assembler.py:197-223`) for 422-on-unknown-exercise validation, and the router's existing `_coach_club_id`/`_require_coach_or_admin` helpers (`technique.py:186-201, 77-98`) for club-scoping and RBAC — no new cross-cutting code.

**Alternatives considered**: extending the RE-EDIT path in `assemble_technique_session` to accept an existing session id directly (rejected — that path's delete-then-reinsert semantics are wrong for an *additive* attach, and it is coupled to the composer's synthetic-exercise bookkeeping, which is out of scope here and slated for removal); routing the new endpoint through `training_sessions.py` (rejected — crosses module ownership boundaries for no benefit, breaks the established per-domain-router convention strength and intervals both follow).

## R2. Backend gap analysis — strength (no gap; frontend-only)

**Decision**: No backend change needed for strength. `POST /api/strength/blocks/{id}/attach` already attaches a block to an existing session. The only gap is that `BlockBuilderPage.tsx` never preselects the session the coach came from, and there is no lightweight "pick an existing block" screen (see R7).

**Evidence**:
- `backend/app/routers/strength.py:440-472` (`attach_block`) — body `AttachIn{training_session_id}` (`backend/app/schemas/strength.py:143-146`).
- `backend/app/services/strength/blocks.py:528-615` (`attach_block_to_session`) — 404 on unknown/foreign-club block or session (lines 564-585), then 409 when the `(training_session_id, block_id)` pair already exists (lines 587-597) **before** inserting, backed by `UniqueConstraint("training_session_id", "block_id", name="uq_strength_session_block")` (`backend/app/models/strength.py:314-318`). This is a clean idempotency-by-conflict pattern: a lost-response retry gets a deterministic 409, never a duplicate row.
- Frontend gap confirmed: `frontend/src/routes/strength/BlockBuilderPage.tsx:80-113` reads only `useParams<{id}>` for the block id — no `useSearchParams`/`location.state` read anywhere in the file. The attach panel (`:283-398`) always renders a full searchable `role="radiogroup"` list of every club session (`:355-377`), never pre-filtered or pre-selected, even when the coach arrived via "Armar bloque de fuerza" from a specific session (`frontend/src/routes/training/SessionDetailPage.tsx:774-779`, a plain `<Link to="/strength/blocks/new">` with no query param or state).

**Rationale**: fixing this is a frontend routing/prefill change only (R5), not a backend contract change.

## R3. Backend gap analysis — intervals (reference pattern; no change)

**Decision**: No change. Intervals is the pattern the other two are unified onto.

**Evidence**: `IntervalStructure` carries `UniqueConstraint("training_session_id", ...)` (`backend/app/models/interval_structure.py:90-95`) — literally 1:1 with a session. `POST /api/intervals/structures` (create, body includes `training_session_id`) and `POST /api/intervals/templates/{id}/attach` (copy-on-attach into a new structure, `backend/app/routers/intervals.py:543-581`) both operate directly against the session already in view — no separate page, no search-then-attach step. `frontend/src/components/intervals/TemplatePicker.tsx` (full component) is the concrete UI reference: filter bar → grid of cards → per-card "Adjuntar a la sesión" button with inline pending/error state (`:580-645`), wired to `AgeGateDialog` at the point of 422 failure (`:262-265, 409-421`). This is the shape R7/R10's new pickers generalize.

## R4. New endpoint contract shape & idempotency strategy

**Decision**: `POST /api/technique/sessions/{training_session_id}/exercises` inserts new `TechniqueSessionExercise` rows for items not already present, and silently no-ops (does not duplicate, does not error) items that already match an existing `(training_session_id, exercise_id, segment)` combination. New items are appended after the current highest `position` in their segment.

**Rationale**:
- `TechniqueSessionExercise` (`backend/app/models/technique_exercise.py:256-293`) has **no unique constraint** on `(training_session_id, exercise_id, segment)` — only an index on `training_session_id` (line 266). Unlike strength's `uq_strength_session_block`, a naive retry of a failed-in-flight attach call *would* insert literal duplicate rows today. Since FR-009 explicitly requires "retry without duplication," the new endpoint must defend against this itself.
- An application-layer "check-then-skip" (query existing rows for the session, filter the incoming batch down to genuinely-new tuples before inserting) requires **no migration** (unlike adding a DB unique constraint + catching `IntegrityError`, which strength uses but which would need a new constraint here). Given the plan's expectation of zero schema change, the app-layer approach is preferred.
- It is also better UX for a **batch** attach (the spec's "multi-select w/ per-item params"): a partial repeat inside one call (e.g., the coach double-taps "Agregar" and the same 3-item batch is submitted twice) degrades to a no-op for the repeated items rather than failing the whole batch on a single conflicting row.
- Response reuses the existing read shape: `{ mixes_age_bands: bool, items: TechniqueSessionItem[] }` — the full current list (not just the newly-inserted delta), so the frontend can replace its cache wholesale exactly as `get_session_exercises` already returns it (`assembler.py:525-573`), keeping the contract symmetric with the existing `GET`.

**Alternatives considered**: add `UniqueConstraint(training_session_id, exercise_id, segment)` + 409-on-conflict (rejected only because it requires a migration where a migration-free option exists; noted here as the "if a migration is ever justified for other reasons, do this too" fallback — not needed for 032); returning only the newly-created delta (rejected — forces the frontend to merge two different response shapes depending on call site, more error-prone than "always return full current state").

## R5. Preselect mechanism: `?session_id=` query param (decided over `location.state`)

**Decision**: When a build/attach screen is opened from a session, the originating session id travels as a URL query parameter (`?session_id=<id>`), not React Router `location.state`.

**Evidence for both options already existing in this codebase**:
- Query-param prefill precedent: `frontend/src/routes/calendar/EventFormPage.tsx` already reads a prefill query param (`?date=`), populated by `CalendarPage.tsx`'s day-click handler (documented as a fixed bug in `docs/17-coach-ux-redesign/proposal.md` §3.2 and `specs/028-frontend-design-foundation/research.md` R11: "Calendar day-click: fill the empty `handleDateClick`... `EventFormPage` already reads `?date=`"). 13 files in `frontend/src/routes/` use `useSearchParams` (grep), including both tab-sync usages this feature also copies from (R8).
- `location.state` precedent: used exactly once in the entire frontend, `frontend/src/routes/training/SessionFormPage.tsx:38-41`, for a one-shot AI-assistant draft handoff consumed immediately on mount.

**Rationale for choosing the query param over the existing `location.state` precedent**: the AI-assistant handoff is consumed once, on arrival, from a screen the coach is not expected to reload mid-flow. Our case is different — a coach mid-way through picking exercises for a strength block on a tablet, in the field, on intermittent 3G/4G (CLAUDE.md non-negotiable constraint), can plausibly refresh or have the tab reclaimed by the OS before finishing. `location.state` evaporates silently on reload, dropping the coach back to a generic, unpreselected form with no error and no explanation — precisely the kind of silent failure Constitution III forbids ("no silent failures"). A query parameter survives refresh, is shareable/bookmarkable, and requires no new mechanism the project doesn't already use in the same file family (routes/calendar, routes/training, routes/athletes, routes/competitions all already read search params).

**Application**: `/strength/blocks/new?session_id=123` — `BlockBuilderPage` reads `session_id` via `useSearchParams`, pre-fills and locks the attach target (shows it as a resolved, read-only summary — same "locked read-only summary" pattern feature 015 established for prefill-import, per CLAUDE.md's technical-notes entry for `specs/015-prefill-import-from-competition`), and on successful attach returns the coach to `/training/sessions/123?section=plan` (R8) rather than showing the generic "Ver sesión / Seguir editando" choice it shows today (`BlockBuilderPage.tsx:303-329`) — FR-002's "returns the coach to the session" is satisfied directly.

Technique needs no separate build page at all under the unified model (R1/R6): the picker lives inline in the session's Plan section, so there is no page navigation to preselect — the session id is already the page's own route param (`/training/sessions/:id`).

## R6. Library-initiated attach (US1 scenario 5) and the session picker

**Decision**: One shared "which session?" picker component, reused at both entry points (from a session — id already known/locked; from the library — id unknown, must be asked), backed by the existing `useTrainingSessions` hook with no new backend endpoint.

**Evidence**: `frontend/src/api/trainingSessions.ts:80-94` (`useTrainingSessions(filters?)`) already accepts `from_date`/`to_date`/`status`/`athlete_id` filters against `GET /api/training-sessions` (`backend/app/routers/training_sessions.py:323-346`, both `from`/`to` optional — confirmed via `Query(default=None, alias="from"/"to")`, lines 324-325). `BlockBuilderPage.tsx:107-112` already calls this same hook with no filters and does client-side text search; the only change needed is to bias the picker toward **recent/upcoming** sessions (`status=planned`, `scheduled_date` near today) instead of the unfiltered/searchable-by-text list it renders today.

**Important ordering gotcha found in the service layer** (also feeds R10): `backend/app/services/training/sessions.py:905-910` orders the default list **descending** by `(scheduled_date, scheduled_start_time, id)` — i.e., the furthest-future session first, matching a general "browse the list" use case, not a "what's next" use case. Any "recent/upcoming" picker (here and in R10's "hoy" fallback) **must not** rely on API order; it must sort the fetched window client-side ascending by `(scheduled_date, scheduled_start_time)` before presenting "next 5" or "take the first."

**Application**: from a session, the picker step is skipped (id already resolved from the route). From the library (technique catalog or `/strength/blocks/new` with no `?session_id=`), the coach sees a compact list of upcoming sessions (next ~5, ascending, `status=planned`) with a "buscar" fallback for anything further out, exactly the same list-rendering component in both places. Selecting a session either (a) for strength: client-side `navigate('/strength/blocks/new?session_id=' + id, { replace: true })`, converging to the exact same state as R5's direct-preselect case — one code path, or (b) for technique: the picker's confirm directly calls the new attach endpoint (R4) since there is no separate build page to route to, then offers a "Ver en la sesión" link to `/training/sessions/{id}?section=plan`.

## R7. Strength gap: no "pick an existing block" screen exists yet

**Decision**: add a new, lightweight component mirroring `TemplatePicker.tsx` — a filterable list of the club's existing (non-archived) strength blocks with a one-click "Adjuntar a la sesión" per card, calling the already-existing `POST /api/strength/blocks/{id}/attach` directly. No backend change.

**Evidence**: `GET /api/strength/blocks` (`backend/app/routers/strength.py:300-321`) already lists the club's blocks; nothing in the frontend renders them as a pick-and-attach list — `BlockBuilderPage.tsx` only ever shows the full `BlockAssembler` build form, even when a coach just wants to reuse a block they already built. This is the one asymmetry between strength and the intervals reference pattern: intervals offers **both** "Crear estructura" (inline, from scratch) and "elegí un template" (`TemplatePicker`, pick-existing) side by side (`SessionDetailPage.tsx:1001-1036`); strength today only offers the "build new" path.

**Rationale**: closing this gap is what makes strength's attach interaction *identical* to intervals' (FR-001: "one identical interaction pattern... modeled on the current inline interval flow") rather than merely "also attachable." The new picker is presentational + one mutation call (`useAttachBlock`, already exists — `frontend/src/hooks/strength/useStrength.ts:165-184`, invalidates `strengthKeys.sessionBlocks(...)` on success) — no new hook needed beyond a `useStrengthBlocks()`-style list query if one doesn't already exist under that name (verify at task-breakdown time; `GET /blocks` is already consumed somewhere for the catalog/list page and can be reused).

**Alternatives considered**: leave strength "build-new-only" and call the unification done once preselect works (rejected — FR-001 requires the *same* pattern, and the intervals reference explicitly includes a pick-existing path; leaving strength asymmetric would re-create a smaller version of today's 3-pattern inconsistency).

## R8. Session sections: tabs primitive, URL sync, default rule, deep-link mapping

**Decision**: Reorganize `SessionDetailPage.tsx`'s 7 stacked full-width blocks (Header/Detalles/Recorrido/Asistencia/Bloques de fuerza/Estructura de intervalos/Fotos y videos, `SessionDetailPage.tsx:548-1141`) into 4 sections — **Resumen** (details + route + status), **Asistencia**, **Plan** (technique + strength + intervals + plan-vs-actual), **Media** — rendered on the shared `components/ui/tabs.tsx` primitive, with `?section=` synced to the URL using the same mechanism as `AthleteDetailPage.tsx`'s `?tab=`.

**Tab primitive choice — evidence for why `ui/tabs.tsx` and not the other two existing patterns**: the proposal's own component audit (`docs/17-coach-ux-redesign/proposal.md` §2 "Tab-bar implementations | 3 (plain buttons / `ui/tabs` / raw Radix)") is visible in this exact codebase: `AthleteDetailPage.tsx:570-634` hand-rolls `<button>` elements styled as tabs (`tabClasses`/`tabStyle` helpers, no `role="tablist"` semantics beyond manual styling); `CompetitionDetailPage.tsx` imports `* as TabsPrimitive from "@radix-ui/react-tabs"` directly (`:21, 625-692`) rather than the project's own wrapper; `frontend/src/components/ui/tabs.tsx` is the actual shared primitive (Radix-backed, 48px min-height triggers already baked in at line 42: `min-h-11`) but is under-adopted. Per Constitution III ("UI components MUST be sourced from the shared shadcn/ui... system") and the 028 consolidation goal, new 032 code standardizes on `ui/tabs.tsx` and must not introduce a 4th variant or copy either legacy pattern.

**URL-sync mechanism — copied from, not identical to, `AthleteDetailPage.tsx`**: that page's `parseTabParam`/`updateTab`/back-forward-`useEffect` triplet (`AthleteDetailPage.tsx:64-69, 404-426`) is the pattern to copy, renamed to `section`/`?section=` with the fixed value set `resumen | asistencia | plan | media` (vs. that page's 6 athlete tabs). `CompetitionDetailPage.tsx`'s simpler derived-`activeTab`-from-`searchParams` + `handleTabChange` (`:216-231`) is functionally equivalent and confirms this is a stable, repeated in-house convention, not a one-off.

**Default section rule — decided: `asistencia` when `session.scheduled_date` is today (club timezone), else `resumen`.** Justification: the UX audit's single highest-severity Flow 2 finding is that attendance — "the single most-used field-day control" — sits below Detalles/Recorrido in the current stacked layout (`docs/17-coach-ux-redesign/agent-reports/01-ux-heuristics-workflows.md`, Flow 2 first row, severity High). On the day of the session, the coach's first action on opening it is almost always attendance; on any other day (forward planning, after-the-fact review from the office) Resumen is the more useful landing view. This mirrors the "hoy" bias this same feature applies to the sessions list (R10) and the home tile's "Próxima sesión" framing (`docs/17-coach-ux-redesign/proposal.md` §5) — one consistent "today-first" philosophy across the app, not a one-off special case.

**Deep-link mapping**: `/training/sessions/{id}` with no `?section=` → default rule above (FR-008: no address changes for old bookmarks). The interval "Ver comparación plan vs. real" in-page link (`SessionDetailPage.tsx:190-197`, `StructureMatchLink`) and all three content blocks land on `plan`. The separate route `/training/sessions/{id}/activity-match/{activityId}` (`App.tsx:385`) is its own page, not a section of this one, and is unaffected. Any content-attach flow that returns the coach to the session (R5/R6) explicitly targets `?section=plan`.

## R9. Age-band safeguards: reused unchanged, no new gates

**Decision**: the unified attach flow calls the exact same two gate components, at the exact same decision points, with no new gate invented for technique (which has none today).

**Evidence enumerated**:
- Strength: `frontend/src/components/strength/AgeBandGuardrailDialog.tsx` — shown on 422 `AGE_BAND_GUARDRAIL` from `backend/app/services/strength/blocks.py:145-197` (`_validate_age_band_guardrail`), a "warn-and-allow with recorded override" gate (`is_age_override` + `override_note` persisted on `StrengthBlockEntry`, `backend/app/models/strength.py:281-285`). Fires during block **create/update** (`BlockAssembler`'s save step), not during session-attach itself — session-attach (`POST .../attach`) has no age logic at all (it attaches an already-validated block). The unified flow does not touch this call site; it only adds the "pick existing" path (R7) and the preselect (R5), neither of which goes near block creation/edit.
- Intervals: `frontend/src/components/intervals/AgeGateDialog.tsx` — two modes, `confirmation` (`age_gate_confirmation_required`, 10-12 Z1-Z2 requires explicit confirm) and `blocked` (`age_gate_z3_blocked`, hard block, no override), driven by `backend/app/routers/intervals.py` 422 responses from `structures_svc`/`templates_svc`. Already fires inline on the session page today (`SessionDetailPage.tsx` imports `INTERVAL_AGE_BAND_LABEL` from this file at line 36) and stays completely unchanged — intervals is the reference pattern, not something this feature modifies.
- Technique: **no gate exists** — `AssembleSessionResponse.mixes_age_bands` (`backend/app/schemas/technique.py:443-462`) is an informational notice only ("FR-014... age-mix UI notice. La sesión se guarda independientemente de ese valor" — the docstring is explicit that it never blocks). The new attach endpoint (R4) computes and returns this same flag (reusing `_compute_mixes_age_bands`, `assembler.py:226-251`) so the inline picker can show the identical notice, but this is **not** a safety gate and must not be presented as one — scope boundary: this feature does not add a new gate to technique, only preserves the existing notice's parity.

**Rationale**: FR-006/SC-007 require zero regression in gate behavior; the safest way to guarantee that is to not touch the gate components or their trigger conditions at all, only the surrounding navigation/preselect chrome. Verified no gate-adjacent code needs to change for R5/R6/R7.

## R10. "Hoy" shortcut: timezone helper, sort-order gotcha, fallback, visual marker

**Decision**: add a `todayISODate()`/`isToday(dateStr)` pair to `frontend/src/lib/datetime.ts` (reusing the exact club-timezone technique already implemented there), a "Hoy" quick-filter action in `SessionFiltersBar.tsx`, and a non-color-alone visual marker on today's row in `SessionsTable.tsx`.

**Evidence for the timezone mechanism to reuse**: `lib/datetime.ts:1-2` already defines `CLUB_TIMEZONE = "America/Bogota"`; `formatRelativeDay` (`:164-199`) already computes "today" in club timezone via `Intl.DateTimeFormat("en-CA", { timeZone: CLUB_TIMEZONE })` on both the target value and `new Date()`, comparing the resulting calendar days. The new helpers extract this exact technique into small, reusable, exported functions rather than re-deriving "today" a third way (the dashboard's `formatRelativeDate` in `AthleteDetailPage.tsx:106-117` is a *third*, timezone-naive reimplementation of the same idea using browser-local time — not to be copied; `formatRelativeDay`'s club-timezone-correct version is the one to extract from).

**Sort-order gotcha (also feeds R6)**: the default list ordering in `backend/app/services/training/sessions.py:905-910` is `scheduled_date DESC` — furthest-future first. A "hoy" filter that just sets `from=to=today` is fine (a single day has no ordering ambiguity), but the **fallback** ("no session today → offer the next upcoming one," US3 AC2) must not assume the first row of an open-ended `from=today` query is the nearest date — it is the opposite. The fallback logic must fetch a bounded forward window (e.g. `from=today`, `to=today+90d`) and sort the result **client-side ascending** before taking the first entry.

**Visual marker — not color alone (constitution III, WCAG SC 1.4.1)**: today's row/card in `SessionsTable.tsx` gets an icon (e.g. a small "today" badge/dot) **and** a text label, not a background-color change alone, in both the mobile card branch (`:44-116`) and the desktop table branch (`:118-232`) — the file's existing dual-render structure means the marker must be added in both places or it silently disappears on one breakpoint.

**Fallback labeling**: when "hoy" finds nothing today, the resulting view is clearly labeled ("No hay sesión hoy — próxima sesión:") rather than silently showing a next-best match that looks like an exact "today" hit (US3 AC2's "clearly labeled" requirement).

## R11. Feedback standards and retry-safety (028 adoption)

**Decision**: all three attach flows adopt the 028 standards verbatim — pending states (spinner + label, matching the existing `TemplatePicker` "Adjuntando…" convention, `TemplatePicker.tsx:634-639`), `sonner` toasts on settle, and non-duplicating retry. Client-side guard (disable the action while `isPending`, standard TanStack Query behavior already used everywhere in this file family) is the first line of defense; the technique endpoint's server-side dedupe (R4) is the second line, covering the "response lost after the server already committed" case that a client-side disabled-button cannot cover. Strength's attach already has an equivalent second line via its DB-unique-constraint-backed 409 (R2). Intervals is unaffected (unchanged reference pattern, already has its own retry story via `age_gate_confirmed` resubmission, `TemplatePicker.tsx:209-260`).

**Rationale**: this two-layer approach (client debounce + server idempotency) is the only combination that actually satisfies "retry must not attach duplicates" under a real connection-loss scenario (request succeeds server-side, response never arrives client-side) — a client-only guard cannot detect that case at all, since the client believes the request failed.
