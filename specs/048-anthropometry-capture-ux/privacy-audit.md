## Findings

| # | Severity | Location | Finding | Recommendation |
|---|---|---|---|---|
| P-1 | major | `backend/app/schemas/anthropometry.py:53` | `notes: str \| None` has no `max_length`. The frontend Zod caps notes at 2000 (`frontend/src/schemas/anthropometryCapture.schema.ts:79`), but the API does not, so a direct client can send any length. The column is `Text` (64 KB on MySQL). A note over that limit raises a MySQL 1406 `DataError`. The generic 500 handler (`app/main.py:204-214`, `exc_info=exc`) then logs SQLAlchemy's `[parameters: (...)]`, which contains the note text and the measurement values. `create_async_engine` in `app/database.py:27` does not set `hide_parameters=True`. Notes are free text and can hold health remarks, so they are CRITICAL/HIGH data. The POST already had this gap before 048. The new PUT inherits it through `_AnthropometryMeasuresIn`. The offline SQLite lane cannot catch it because SQLite does not enforce the column length. | Add `Field(default=None, max_length=2000)` to `notes` in `_AnthropometryMeasuresIn`, which covers POST, PUT and plausibility. This matches the Zod limit and the contract claim that "ranges are identical" (data-model.md). Add a 422 test for 2001 characters. Separately, and platform-wide (a shared file, not a 048 file), set `hide_parameters=True` on the engine. Not fixed here: it is not a blocker, and the trigger needs a hand-crafted request from an authenticated coach. |
| P-2 | minor | `backend/app/schemas/anthropometry.py:117`, `backend/app/routers/anthropometry_roster.py:139` | The roster returns a full `birth_date` for every athlete in scope. It is justified: the client needs a decimal age at the evaluation date for the PHV preview (`CaptureReviewStep.tsx:153-165`, Mirwald) and for the skinfold age gate (`:171-172`). It is never rendered: `MeasurementSessionPage.tsx` shows only `full_name` and `category`. It is also not persisted to storage (see "OK" below). The same coach already gets it from `GET /api/athletes/{id}`, so it adds no new exposure. It does, however, put about 20 DOBs in one response that exists only for a queue picker. | Optional minimization: return `age_decimal_at_date` (the roster already computes it for `skinfolds_eligible`) and lazily fetch `birth_date` only for the athlete being captured, or compute the PHV preview from the age. Keep it coach/admin-only and never log it. Not required for approval. |
| P-3 | minor | `backend/app/routers/anthropometry.py:551, 559-565` | The PUT 409 bodies for `athlete_too_young` and `skinfold_interval_too_short` reuse the 046 messages. They carry the minimum age in years and the dates of the conflicting skinfold sets. There is no name, DOB or value, and the caller is a coach who already sees those dates. | OK to keep; the shape is the same as 046. Listed only for traceability. |

It comes from `backend/scripts/seed.py` (demo data), not from 048. There are no new 048 e2e specs in the tree yet: `anthropometry-*.spec.ts` are unchanged since `ebbb786`, and another agent is writing them. | Confirm with the owner that the demo-seed names are fictional, and mark them as such in `seed.py`. The new 048 e2e specs must use "Deportista Ficticio"-style names. Not edited, as instructed. |

## Checks that passed (OK)

- **Audit meta and diff.** POST writes `meta={"event_date"}`. PUT writes `changed_fields` (field names only), `diff` only for `evaluation_date` (in `VALUE_ALLOWLIST`), and `meta.event_date` (`routers/anthropometry.py:594-616`). DELETE writes `meta={"had_skinfolds": bool}` (`:651-660`), and `had_skinfolds` is added to `META_ALLOWLIST`. Deleting AI explanations writes ids only (`related_entity_id`). The PUT and DELETE route keys are `Audited`. The plausibility dry-run is `Exempt` with a reason. The roster is a read and is not audited (FR-005).
- **Logs.** None of the new backend modules log anything. `anthropometry_plausibility.py` is pure, and `anthropometry.py` has a docstring saying it never logs values. There is no `console.*` in the feature's frontend files. `test_logs_never_contain_measurements_or_names` sweeps PUT 200/422/409/403, the plausibility check, the roster 200/422 and DELETE at DEBUG level, including `extra=`.
- **4xx bodies.** They contain stable codes only: `anthropometry_same_date_exists` plus `existing_record_id`/`same_values`, `not_record_author`, `anthropometric_record_not_found`, `roster_date_in_future` and `sitting_ratio_impossible`. The Pydantic messages never interpolate the submitted value. The global 422 handler drops `input` and `ctx`. `test_anthropometry_privacy.py` asserts that ten error responses are clean.
- **Parent payloads.** `can_modify` and `plausibility_flags` use `exclude_if=lambda v: v is None` and are set only for admin/coach (`routers/anthropometry.py:476-487`). The keys are omitted for parents and pinned by three tests. `notes`, `morphology` and `skinfolds` are still nulled for parents. Any other endpoint that serializes `AnthropometryOut` leaves both fields at their `None` default, so they are omitted there as well.
- **Parent reachability.** PUT, DELETE, plausibility and roster all use `require_role([admin, coach])`, and each has a parent-403 test. `can_modify_anthropometric_record` returns false for anyone except the author coach or an admin, and runs after `verify_athlete_access` (club scope, and 404 for archived athletes). On the frontend, `/athletes/:id/anthropometry/new`, `/:recordId/edit` and `/anthropometry/session` are wrapped in `ProtectedRoute allowedRoles={[coach, admin]}`. The History edit and delete controls also require `can_modify === true`.
- **Roster scope.** The roster excludes archived athletes. A coach sees only clubs where they hold `ClubRole.coach`, and a coach with no clubs gets `[]`. It returns no measurement values or skinfold readings: only the site columns are read, to decide eligibility.
- **Session store.** `measurementSession.store.ts` is a plain `create()` with no `persist`. It holds only ids, statuses and booleans: no names and no values. `auth.store.logout()` calls `reset()`, and every forced-logout path (refresh failure, 401) goes through `logout()`. The test "logout() del auth store limpia la jornada" covers this.
- **Storage.** The only `localStorage` keys are `tyr.anthro.captureMode` (`guided|quick`) and `tyr.anthro.benchHeightCm` (the bench height, a device setting and not athlete data). The roster (`anthropometry-roster`) and `["anthropometry", id]` queries are not in `PERSIST_ALLOWLIST_PREFIXES`, so they never reach the persisted query cache.
- **URLs.** Routes carry only numeric ids. `?returnTo=` is allow-listed to exactly `/anthropometry/session` (`SkinfoldCapturePage.tsx`), so it cannot be used as an open redirect.
- **Forms.** `DecimalInput` sets `autoComplete="off"` and `inputMode="decimal"`.
- **Fixtures.** Backend fixtures use "Deportista Ficticio N", "Test User" and `@test.com` emails. The feature's frontend tests use "Deportista Uno…Cuatro", "MENOR_B" and "Atleta Demo". The adult staff names found in `src/test/msw/*` are pre-existing and not part of 048.
- **Static content.** `anthropometry_measures.json` and the field-guide template contain protocol text only, with no athlete variables. `template_registry` now requires only the `precheck` and `basic_measures` keys.
- **Images.** I viewed all eight images: four webp and four PDF PNGs. Each shows a generic grey silhouette with no facial features, no text, letters or numbers (the scale ticks are unlabeled), and no logos. `strings` found no EXIF, XMP or C2PA metadata.
- **Illustration prompts** (`quickstart.md` §4). They are generic ("~12-year-old proportions, not identifiable", "no facial features", "no text"). The only reference upload is the in-repo skinfold illustration. No athlete data, photo or name is used.

## Follow-up (2026-09-29, orchestrator)

- **P-1 fixed**: `notes` now has `Field(default=None, max_length=2000)` in `_AnthropometryMeasuresIn` (covers POST, PUT and plausibility); `test_notes_capped_at_2000_chars` asserts 2000 accepted / 2001 → `string_too_long`. The platform-wide `hide_parameters=True` on the engine remains a separate, non-048 recommendation.
- `test_logs_never_contain_measurements_or_names` was flaky (≈1 in 9 runs): it scanned float timing fields of `LogRecord` (`created`, `msecs`, `relativeCreated`), whose digits can contain a token such as «81.9» by chance. Those fields are now excluded; 6 consecutive runs green.
